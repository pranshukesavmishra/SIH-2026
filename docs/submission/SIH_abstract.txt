When two mobile terminals talk to each other with a laser, the beam is narrower than a pencil line at the far end. If the pointing slips by a fraction of a milliradian, the link drops. Before a fine-pointing stage can hold the beam that precisely, a coarse stage has to do three harder, messier jobs first: find the partner terminal's beacon, make sure it is the right light and not a star, a street lamp or a reflection, and keep the aim steady while the platform moves, the beacon blinks and every command arrives about 40 ms late. Today this is usually handled with special optical sensors or with slow manual realignment. Our project, ZeroDrift, is our answer to PS SIH26169: software that does this coarse alignment with an ordinary camera.

The core idea is simple. We do not trust the brightest light. The partner terminal's beacon blinks at 4 Hz, so we look for that rhythm. Every point of light in the image is followed over time, and a light is accepted as the beacon only when its blink pattern matches and a small neural verifier agrees. Steady lamps, stars and glints fail this test and are rejected, however bright they are.

The pipeline runs as one closed loop at 30 frames per second. Each frame is cleaned with a top-hat filter, candidate lights are found with a matched filter and CFAR thresholding, and each one is located to sub-pixel accuracy. Once the beacon is confirmed, an IMM Kalman filter tracks it and predicts where it will be during blink gaps, and a Smith predictor compensates for the command delay. The pointing error is measured directly on the camera image, and because the camera moves with the pointing mount, the loop closes optically: camera, detect, identify, predict, point, and back to the camera. Azimuth and elevation commands go to a physical gimbal (stepper motors driven by an Arduino over Web Serial) or to a virtual viewport. A small state machine (search, acquire, track, coast, re-acquire) decides what to do when the beacon disappears. A short loss is bridged by prediction, and a longer loss starts a spiral search.

A key design choice is that the same tracking engine runs in three places without changing the core code. The first is a physics-based virtual camera that uses real ISS orbits (SGP4), atmospheric turbulence and decoy lights, so we can run large randomised tests that would be impossible to repeat on a bench. The second is a live laptop webcam in the browser, which shows the same pipeline working on real camera images. The third is a physical terminal. Our MK1 servo rig has been built and demonstrated, and the MK2 stepper gimbal with an angle sensor for closed-loop operation is being built now.

Every number we report comes from logged runs. Across 64 randomised ISS-like passes, the system acquired the beacon every time (100%), with a median time to lock of 1.27 s, a 95th-percentile time of 2.77 s and a worst case of 4.0 s. Median lock retention was 97.5%. In none of the 64 runs did it lock onto a wrong light (0 / 64). On the featured demo run, the median pointing error while locked was 198 microradians, and the median of the per-run 95th-percentile error was 768 microradians. The neural verifier reached an AUC of 0.957, against 0.900 for the classical blink test on the same short-window data. The whole pipeline needs 8 to 21 ms per frame on two CPU cores, well inside the 33 ms frame budget, so it runs in real time. The code has 251 automated tests, of which 250 pass and 1 is skipped.

We also modelled the full link. With a fine-pointing stage added after ours, link closure reaches 99.3%, compared with 14.7% for the coarse stage alone, with a mean link margin of 3.1 dB. We state clearly that these are model results, not an end-to-end measurement of an optical link.

Testing in software is also cheap. The full 64-run campaign uses about Rs 0.22 of electricity and runs roughly 207 times faster than the same tests on a hardware bench, so we can try new ideas many times before touching the rig.

In short, ZeroDrift picks the beacon by how it behaves, not by how bright it is. It cancels command delay inside an image-based closed loop, and it moves from simulation to webcam to real hardware with the same engine. The project is open source, and the live demo, replay console and source code are available for review.
